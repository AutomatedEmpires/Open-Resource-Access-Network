## Top design-confusion offenders (ranked)

1. The urgent-help chat funnel silently eats the seeker's words. Home's 'Urgent support' chip, the Google SearchAction, and every /chat?q= link only prefill the composer — nothing ever auto-sends — and for a returning visitor the prompt is discarded outright, because ChatPageClient reuses the stored session id and ChatWindow applies initialPrompt only to message-free sessions (ChatPageClient.tsx:40-47, ChatWindow.tsx:1136-1141). Worse, the app's own suggested query 'I need urgent support' trips the weak-query clarifier ('support' matches the weak regex, no intent keyword does) and burns 1 of the 10 anonymous daily messages (orchestrator.ts:1151-1155, route.ts:81-85). A founder-led fix would make seeded prompts open a fresh session and auto-send (or at minimum retarget the urgent entry points to the directory, which does auto-run), and exempt the app's own suggestions from the clarifier tax.

2. Desktop and mobile ship two different products. The desktop primary nav is Chat/Directory/Map; the seeker mobile bottom bar is Chat/Map/Scroll/Profile (AppNav.tsx:82-86 vs ScopedMobileNav.tsx:30-35). Directory — the documented 'fast searchable list' — has no mobile bottom-nav path, and Scroll is invisible on desktop except via one home-hero button; the command palette and footer omit it too. Docs define exactly three discovery surfaces; the build has four with no canonical story, so a seeker who learns the app on a phone literally cannot find the same surfaces on a laptop. The founder needs to rule which browse surfaces are canonical and make both navs, the palette, and the footer tell one story — parity links are trivial once that call is made.

3. The home 'Browse by need' chips and the directory speak different taxonomies, so the handoff always fails. Fifteen chips pass free-text ?q= while the directory activates categories only from ?category= against its own 12-need taxonomy (page.tsx:47-63, discovery.ts:155-175) — tap 'Mental Health' on home and you land on a page whose identically-labeled 'Mental Health' chip is unselected under 'Start with a common need', inviting you to choose again, and four home chips (Clothing, Immigration, Disability, Veterans) have no directory category at all. One chip mid-grid ('Urgent support') even switches surface to chat. Founder fix: one taxonomy owned in one place, home chips deep-linking ?category=, and the surface-switching chip visually separated.

4. A shadow estate of built-but-unreachable surfaces. /plan can be filled from 'Add to plan' on every card but appears in no nav, menu, or palette; /plan/dashboard has zero production inbound links even with all flags on; /appeal's only reference in the whole codebase is a workflow-engine notification URL; /report is orphaned outside chat cards and can't even be submitted without ?serviceId; /org/[id] is a full SEO page that nothing links to, the sitemap omits, the middleware regex accidentally gates behind sign-in, and that renders with no app shell; /onboarding is reachable once, at signup, forever; and a complete NotificationBell — the entry point that would rescue three of these flows — has zero production imports. The founder should triage this list into 'wire it in' or 'cut it'; every orphan is invisible product work.

5. The Map's first impression is 'ORAN has nothing here.' hasSearchContext() throws away the bounds argument, so browse-by-area is impossible — Search and 'Search this area' stay disabled until a need is chosen — while the overlay simultaneously says 'No mappable resources in this view yet.' on a map where no search has run (MapPageClient.tsx:312-320, LeafletFallback.tsx:305-314). The map also silently discards the record-confidence filter carried from the directory and shows a second, unexplained trust metric (ConfidenceRing % beside the High/Likely/Possible badge). Founder call: allow bbox-only search like every map product seekers know, align the filters with the directory, and until then make the empty state say 'pick a need to load resources', not 'nothing here'.

6. The become-a-host funnel is a chicken-and-egg lockout. /partnerships/organizations promises 'You'll be prompted to sign in before the claim form opens', but new accounts are role 'seeker', the host layout renders AccessDenied below host_member, and host_member is only granted via an existing organization membership — which requires an approved claim (organizations/page.tsx:120-135, HostLayoutShell.tsx:72-78, session.ts:60-77). The denial screen then tells the org's own representative to 'contact your administrator' in raw role-code language. No real provider can ever enter, which starves the seeker side of the network. This needs a founder decision on letting authenticated seekers open the claim workspace.

7. Internal vocabulary is shipped verbatim to people in crisis. Seekers browsing for rent help meet 'Publication-gated records', 'Results come only from stored records with positive publication authority', 'broaden record-confidence filters', and 'These match what the API validates' (DirectoryPageClient.tsx:673,977-981; MapPageClient.tsx:1230,1778); chat explains its privacy model as 'Private chat wording stays here, so broader results may appear'; AccessDenied prints 'requires the host_member role or higher'; and portal headers wear a 'Mobile-first' badge promising navigation 'without horizontal overflow'. A founder-led plain-language pass with a simple rule — no word a case worker wouldn't say aloud to a client — would fix all of it as reversible copy.

8. Nothing is called the same thing twice. One feed is 'Scroll' / 'Scroll resources' / 'Resource Feed' / 'Resources for your next step' (with Directory's own List icon on its hero button); the flagship surface is 'Chat' / 'Chat Assistant' / 'Find services' / 'Get Help'; the recruitment area is 'Work with us' / 'Get Involved' / 'Partnerships'; 'Submit a Listing' opens 'Submit a Resource'; 'List Your Organization' goes two different places from identical labels; both admin roles wear the same 'Admin' badge while the community role is also 'Community volunteer' and 'ORAN Community Admin'; and three portals each have a 'Forms' pill opening three differently-titled pages. Every rename is a safe copy fix, but the naming system itself — one name per surface, label always matches page title — needs the founder to set and enforce the vocabulary.
